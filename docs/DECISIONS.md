## 2026-10-20 D004 Markdown タスクの書き方
- 原本はノート本文の `- [ ]` 行。別 DB を持たない（Agenda は派生）。
- 印は Obsidian Tasks と互換にした: 期限 `📅`、予定 `⏳`、開始 `🛫`、完了 `✅`、繰り返し `🔁`、優先度 `⏫🔼🔽`。絵文字を打ちにくい環境向けに `due:` `scheduled:` `start:` `done:` `repeat:` も読む。依存は `id:` と `after:`。
- 理由: 既存のふつうの Markdown タスク（印なし）はそのまま読める・書ける。他アプリとの往復で壊れない。
- 代替案: YAML front matter にタスクを持つ → ノート本文との二重管理になるので不採用。
- 繰り返しの完了は「完了した行の下に次の回の未完了行を作る」（履歴が残る）。基準は期限（無ければ予定、どちらも無ければ完了日）。

## 2026-10-20 D006 【承認済み・簡素化】`\A` の GUI 編集モード
- **利用者の指示（2026-10-20）: 「GUI を起動しているときは GUI だけ」。** 3 モード（Real Vim / GUI 編集 / 閲覧専用）は同じウィンドウで選ぶ排他のモードで、同時に 2 つが動くことはない。したがって下の「書き込み権（lease）」は不要。実装は **「モード切替の瞬間に保存 → 新しいモードが読み直す」だけ**。
- 気にするのは GUI の外（別端末の Vim・スマホ取り込み・別ウィンドウ）が同じファイルを書く場合だけ。これは既存の `gnosis#conflict`（上書き前の確認・未保存内容の退避）と、GUI の保存時の「読んだときの内容ハッシュ」の照合で守る（食い違えば保存せず差分を出す）。
- GUI 編集の保存でも、Vim の保存時と同じ Python の同期（`note_format_v2.py update_one`）を走らせる（二重実装しない）。
- 以下は元の提案（経緯として残す）。

## 2026-10-20 D006 元の提案（上記で簡素化）`\A` の GUI 編集モードと書き込み権
- 問題: 原本 §4.2 は「Real Vim / GUI 編集 / 閲覧専用」の 3 モードを求める。一方 §4.2 は「1 つの原本に同時に 2 つの独立した書き込み主体を許さない」とも求める。現状の `\A` は Vim が唯一の書き込み主体。
- 提案: ノートごとの**書き込み権（lease）**。Vim か GUI のどちらかだけが持ち、切替時に保存・内容ハッシュの記録・読み込み直しを行う。GUI の保存は期待ハッシュつきで、食い違えば保存せず競合を返す。詳細は ARCHITECTURE.md「Phase 2 設計案」。
- 代替案: (1) GUI 入力を Vim へキー列で送る → 却下（脆い）。(2) CodeMirror を常に主にして Vim を従にする → 「本物の Vim 中心」の不変条件に反するので却下。(3) GUI 編集を作らない → 要件違反。
- 影響: データを書く経路が増える。実装前に承認が要る。承認までは **方針 A（ペイン層・表示専用ビュー・コマンドパレット）だけ**を進める。
- 承認してほしい点: ① 書き込み権の方式でよいか ② 競合時の既定（保存しない・差分を出す）③ GUI 編集の保存でも Gnosis の同期（関係ブロックの整合）を走らせてよいか。
